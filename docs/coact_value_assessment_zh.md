# coact 组件价值评估

结论：coact 的价值不在 C++17，而在把事件驱动系统的执行顺序、容量上限和失败路径
变成结构约束。它适合中等复杂度、单核、要求可验证的工业控制，不适合极小固件或
需要认证 OS 的场景。

## 1. 核心价值

- 单 Dispatcher、静态 HSM、定容事件池，让“谁先执行、队列满怎么办、失败怎么回滚”
  由框架统一决定，不再依赖每个模块的约定。
- 零堆、无异常、无 RTTI，线程、队列、事件池都是静态对象，内存上限在编译期确定。
- 准入、熔断、监控、故障复位是框架的一部分，能直接产出评审需要的测试证据。

## 2. 已具备的证据

| 项目 | 结果 |
|---|---|
| host 测试 | 60 项通过 |
| Renode 准入夹具 | 231/231 |
| Renode FreeRTOS PAL | 32/32 |
| Renode FreeRTOS 故障路径 | 8/8 |
| Renode MPU 能力矩阵 | 13/13 |
| 变异测试 | 全部被捕获 |

这些数字说明机制成立，但不能替代硅片验证和产品长期运行数据。

## 3. 成本

| 配置 | Flash 增量 | RAM 增量 |
|---|---:|---:|
| 默认配置 | +8.8 KiB | +9.3 KiB |
| 小配置 + LTO | +7.9 KiB | +6.3 KiB |

Dispatcher 栈为 4 KiB，实测高水位 976/1024 字，余量约 192 B。动作链更深的
产品必须重新测量并加大栈。对 32 KiB Flash 的小板子偏重，对 128 KiB 以上的
工业板可以接受。

## 4. 与替代方案比较

| 方案 | 优势 | 不足 |
|---|---|---|
| 手写 FreeRTOS 任务加队列 | 体积小、直接 | AO 生命周期、背压、回滚和测试证据要自己补 |
| QP/C++ | 生态成熟、建模工具和文档完整 | 工具链和框架约束更重，RT-Thread/FreeRTOS 适配需要额外工作 |
| AUTOSAR OS | 保护域、OS 钩子、认证路径完整 | 不是同类组件；coact 不能当安全 OS 使用 |

## 5. 适用与不适用

适用：

- 多个主动对象、状态机较多、任务和 ISR 混合提交。
- 需要背压、确定性唤醒、可测的失败路径。
- 需要通过安全评审，要求无堆、故障有界复位。

不适用：

- 只有三五个任务、逻辑以顺序流程为主。
- Flash 预算低于约 64 KiB，且不需要 AO/HSM。
- 需要 AUTOSAR 保护域或功能安全认证。

## 6. 当前短板

- 只支持单核，Dispatcher 栈接近下限。
- v0.7.0 尚未积累长期产品运行数据。
- BSP 钩子、保护域和认证语义要由产品补，框架只提供契约和证据入口。

一句话：coact 是一个取舍明确的工业事件框架。项目确实需要它那套结构时，价值成立；
如果只是少量任务加队列，手写 C 更划算。
