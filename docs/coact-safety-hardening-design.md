# coact 可靠性增强设计：准入、隔离前提与受控恢复

结论：保留 coact 的协作式事件模型，不移植 AUTOSAR 调度器，也不引入完整用户态。以自研、可信业务代码为前提，采用 MPU 防误写、线程栈 guard、代码与常量只读保护、数据不可执行、API 边界、准入监测和 watchdog。异常后局部重启另设条件，不能用“派发前后切 MPU”承诺共享栈损坏后的恢复。

状态：P1 已实现，并在 host 与 Renode Cortex-M4 模型上完成验证；P2 至 P4 仍为提案。评估与实现日期：2026-11-02；设计基线：`73fe452`。P1 落点为 `include/coact/admission.hpp`、`include/coact/coordinator.hpp`、`include/coact/runtime.hpp` 和 `include/coact/monitor.hpp`，实测数据见第 8.1 节与 `test/renode/README.md`。以下源码位置均对应本地快照，不代表参考系统的认证结论。

## 1. 评审结论

原稿方向可保留，但不能直接作为实现契约。以下问题按阻断程度排序。

| 等级 | 原稿问题 | 源码依据与修订 |
|---|---|---|
| 高 | 没有明确可信代码前提，却承诺 AO 只能访问授权内存 | 采用特权态 MPU 防误写，不把 API 约束描述为不可绕过的特权隔离，见第 5 节 |
| 阻断 | 假定每个 AO 有独立栈，异常后可直接恢复 Dispatcher | `include/coact/ao.hpp:329` 同步调用 HSM，`include/coact/runtime.hpp:158` 仅配置 Dispatcher 栈；共享执行栈损坏时不具备局部恢复前提 |
| 阻断 | 派发返回后采样被称为时间保护 | `include/coact/dispatcher.hpp:212` 与 `include/coact/coordinator.hpp:191` 都依赖处理函数返回；死循环无法靠该机制终止 |
| 高 | 把 Breaker 写成全局机制，把池写成唯一全局池 | 默认 Runtime 使用逐 AO 的 `BreakerBank`；已有多池注册，见第 2 节 |
| 高 | 将最小到达间隔定义为派发开始间隔 | 队列积压后集中出队会误报；应在提交准入处检查，与调度节流分开 |
| 高 | 忽略直发、在途提交及跨域事件引用 | 生产者可直接执行 AO，拒绝和直发路径也回收事件；恢复必须覆盖全部持有者，见第 6 节 |
| 中 | 一次新增四个安全头文件和多个架构后端 | 实际只新增一个 `admission.hpp`，复用现有 Config、Coordinator、Monitor 与 PAL；硬件后端待目标板确认后再定义 |

默认选择轻量防护路线：软件准入与板级 MPU 防误写可以分别实施，不以用户态为前置条件。P1 已经按这条路线落地；只有产品要求业务无法绕过保护，或任意业务异常后其他域仍可继续运行时，才评估更强执行边界及独立恢复机制，二者不属于当前默认范围。

## 3. 范围与架构约束

### 3.1 第一阶段包含

以已有 Coordinator、Staging、Dispatcher、BreakerBank 为主线，补充准入与故障可观测性。逻辑域表示一组静态 `TargetId`，不是硬件内存域；优先用板级 const 表表达归属，不给每个 AO 增加未使用字段。

| 能力 | 默认值与行为 | 不覆盖的风险 |
|---|---|---|
| 最小到达间隔 | 未配置时关闭，原有提交行为不变 | 不能阻止业务处理函数死循环 |
| 每 AO 积压上限 | 未配置时保持现有队列容量限制 | 不提供内存写隔离 |
| 故障快照 | 槽数由 Config 显式配置，默认 0 槽（一个空成员，无记录存储）；记录目标、路径、原因、时间和预算 | 不能自行恢复损坏的执行栈；撕裂读取按诊断失败处理 |
| 合作式停域 | 显式配置才启用，仅在可信代码可继续执行时处理 | 不适用于任意 MPU 异常和栈损坏 |

快照槽数与准入策略是两个独立开关：只配置槽数而不启用 `StaticAdmission` 时，环不会被写入，属于配置错误；P1 不为这种组合做运行时探测，避免 Monitor 依赖策略类型。

信任假设：业务代码由项目维护，允许代码缺陷，但不将其视为恶意代码；业务按 API 使用驱动和内核对象，不主动关中断、改 MPU 或任意改写框架内部状态。代码审查和静态检查约束这些行为，但不能覆盖所有控制流跑飞风险。

不引入第二套 Task、Alarm 或 OS-Application 调度。RTOS 仍调度线程，Dispatcher 负责排队事件，Coordinator 可按现有契约直发；不能笼统称 Dispatcher 是所有 AO 的唯一执行入口。

### 3.2 暂不包含

不新增动态分配、异常、RTTI、工厂或通用安全适配层。不实现 AUTOSAR API、完整 syscall、用户栈/内核栈切换或通用指针校验框架，不为未选定平台同时实现 ARMv7-M、ARMv8-M 和 PMP。不承诺功能安全认证、故障独立性或故障后其他 AO 无条件继续执行。

## 4. 准入与时间监测

### 4.1 到达间隔

最小到达间隔 `min_arrival_ns` 定义为同一目标两次成功准入的时间差；首个请求允许，差值等于阈值时允许。默认按目标聚合所有 signal，只有业务明确要求时才细分规则；它不同于允许突发的令牌桶。

检查位于 Coordinator 的共同提交路径，在直发和入队分支之前。按“间隔检查、容量预留、提交成功、提交失败回滚”构成一次提交事务：只有成功直发或成功入队才更新时间，拒绝、满队列和关闭准入不得消耗间隔。

复用 `PolicyOps` 的静态表形式，但现有 `evaluate` 只有单次判定，没有成功提交/回滚通知。因此不能把有状态间隔检查直接塞入该回调就宣称完成；实现时应在现有 Coordinator 提交生命周期补最小事务状态，不另建通用策略引擎。

任务和 ISR 共用规则时，预留与提交状态必须在单核有界临界区中同步，禁止持锁执行 HSM。实现没有采用 64 位原子 CAS：`std::atomic<uint64_t>` 的比较交换在 Cortex-M4 上落到 `__atomic_compare_exchange_8`，没有对应 64 位原子 shim 的裸机链接会缺符号；把它绑到 PAL 临界区又会让“无锁”实际变成隐式关中断，不如直接建模。`ArrivalGate` 因此由四个普通字段组成：最近成功时间、最新在途时间、在途计数、是否成功过。每次更新都在一个 `CriticalSection` 内完成。同步后端由策略类型显式选择，没有默认值：单核目标用 `AdmissionIrqSync`（PAL 关中断，要求该 PAL 的 `irq_save` 真正屏蔽中断），SMP host 验证用 `AdmissionSpinSync`（策略持有的自旋锁，不得与 ISR 共享）。`StaticAdmission` 没有默认构造函数，也不能拷贝或移动；`DispatchCoordinator` 同样禁止拷贝。忘记绑定后端、或复制出一份独立门状态，都是编译错误。

回滚采用持有计数模型，而不是“保存旧值再写回”。屏障取 `holds_ != 0 ? hold_ns_ : last_admit_ns_`：存在在途预约时，后续到达与最新预约比较；没有在途预约时才与最近成功提交比较。失败只减少计数，不写时间戳，因此多个预约交错失败时不会把某个失败预约的时间戳恢复成窗口。`commit()` 只在成功路径调用，并以取最大值的方式更新窗口，乱序提交不会把时间推回。这里有一个刻意保留的保守性：多个预约重叠时回滚最新那个，不会把屏障降到次新的在途预约，因此可能多拒绝一个间隔内的到达。要精确恢复在途最大值，需要为每个目标保留固定容量的在途时间戳集合；少放行一个事件是限流器的安全方向，当前不为它增加每目标存储。

另一个已知边界是时钟采样点在临界区之外：提交入口先取 `monotonic_ns()`，再进入门的临界区。若任务在采样后被 ISR 抢占，而 ISR 以更晚的时间提交，任务恢复后会因 `now < barrier` 被拒。这同样只会多拒绝，不会多放行；要消除它需要把时钟读取移进临界区。host 并发测试使用 `AdmissionSpinSync`；Renode 夹具使用 `AdmissionIrqSync`，走真实 PRIMASK 临界区。ISR 不等待、不调用业务恢复回调。

违规默认拒绝本次提交并记录 `DroppedRateLimit`，消费传入引用一次，不更新时间。关键事件不得自动豁免或静默丢弃，需由业务规则明确拒绝后的安全动作；现有 reason 到 disposition 的映射也须用测试锁定，避免顺带更改其他策略语义。

准入策略是 Coordinator 与 Runtime 的模板参数，不是运行时开关：`Runtime<Config, PalT, Profile, AdmissionT>` 把 `AdmissionT` 透传给 `DispatchCoordinator`，默认 `NoAdmission` 时提交路径与历史版本一致。当前不提供运行中切换策略的接口，避免在热路径引入分支和状态迁移。

### 4.2 积压上限

`max_backlog` 表示已接受但未完成的排队事件数量，包含 Dispatcher 持有的 deferred 事件，不包含正在直发的事件。新增限额必须在 pending 发布前原子预留，失败时不增加 pending；禁止用 `load() < limit` 后单独 increment 的竞态检查。

限额不得超过现有计数类型和容量可表达范围。入队失败回滚预留；派发、拒绝旧事件和停域排空必须各释放一次。关闭状态优先于 `qos.critical`，故障域不得靠关键标记绕过停域门禁。

### 4.3 RTC 耗时与死循环

沿用 `rtc_budget_ns()` 与现有 Breaker 阈值。当前前后 `monotonic_ns()` 差值是调用经过时间，可能包含 ISR、RTOS 抢占和租约操作，不是精确 CPU 时间；报告应称“RTC 耗时监测”，不称硬执行预算。

处理函数必须返回后才能报告超时。对于不返回的处理函数，第一阶段只能依赖独立硬件 watchdog 或已验证的平台超时机制进入产品安全状态/复位；不得由同一 Dispatcher 的软件定时事件承担该职责。

如果后续要求异步超时检测，必须先明确墙钟/CPU 时间、抢占扣账、中断屏蔽上限、故障处理延迟及安全动作时限。仅加入定时器中断也不等于能安全中止 C++ 调用栈，更不等于允许局部重启。

## 5. 可信代码下的 MPU 轻量防护

### 5.1 默认保护模型

特权态执行不等于 MPU 无效。对目标硬件允许限制的访问配置只读、禁止访问或不可执行属性，可以捕获相应误写和误执行；必须按特权访问权限验证，不能只配置“非特权禁止”。背景映射、重叠区域和异常期间的保护行为也须按实际配置验证。

默认按实际线程与关键数据布局设置 MPU，而不是假定每个 AO 有独立地址空间。优先保护代码/常量、关键配置、线程栈边界，并将业务数据与栈设为不可执行；代码应可执行且不可写，不能把代码与常量统一设为不可执行。

当前 `Ao` 将 Context、HSM、租约和 pending 放在同一对象中，见 `include/coact/ao.hpp:389`。第一版保持布局与 API 封装，不声称阻止同一可写区域内的对象内越界。只有明确要求硬件保护框架元数据时，才评估数据拆分与受控写入口。

全线程栈 guard 和静态只读区域不要求关闭直发。只有试验按 AO 动态切换可写数据区域时，才在该配置中先禁用直发，并覆盖初始化/entry/exit/action 和回调；否则业务会在生产者线程栈上执行，静态 AO 域配置不完整。

普通共享栈上的 guard 保护 Dispatcher 线程栈边界，不创建每 AO 独立栈。guard 只能捕获命中其保护范围的访问，跳过 guard 的大跨度越界仍可能漏检；魔术字是事后检测。默认故障入口记录并执行安全动作/复位，不从损坏栈恢复调度。

API 封装用于约束正常业务调用，不是硬件权限。仍保留特权态时，业务跑飞后误关中断或改 MPU 是残余风险，由代码检查、保护寄存器访问收口和独立 watchdog 降低风险，不宣称完全消除。

| 切换与恢复 | 静态区域优先；动态区域由平台入口负责屏障、中断窗口和 RTOS 切换协调，保存实际前态、清除残留，失败时不得执行业务 |
| 特权与外设 | API 和静态检查限制业务直接访问寄存器与内核对象；记录特权态可绕过该约束的风险；DMA 等总线主设备另行约束 |
| 能力报告 | 区分无硬件保护、特权态防误写、不可绕过的执行隔离、局部恢复能力；请求能力不具备时初始化失败，不静默降级 |

不冻结原稿 `switch_to()/restore()/last_fault()` 接口。它没有表示前态、失败和异常退出，不足以作为实现契约。优先接入 RTOS 已有保护服务，禁止 coact 与 RTOS 各自重写 MPU 配置、相互覆盖。

已有多池可用于容量隔离，但不自动提供访问隔离。轻量阶段保留现有事件指针与引用计数，不强制跨模块复制；按业务选择专用池。只有要求跨域载荷硬件隔离时，才校验 MPU 粒度，并采用受控复制或经验证的只读借用协议。

共享队列本身不能保护其指向的载荷。可信代码下继续遵守现有所有权契约；若后续引入硬件域，载荷裸指针不能通过浅拷贝获得访问权，须拒绝或转换为经验证的句柄，并定义借用生命周期和重启失效协议。

事件头含 `pool_id/ref_ctr`，见 `include/coact/event.hpp:22`。轻量阶段不改布局，但业务不得自行修改；若引入不可信执行，元数据与载荷布局、静态事件 `pool_id == 0` 的授权规则须另行设计。

### 5.3 与完整用户态的取舍

完整用户态主要解决三件事：应用不能直接访问内核对象，不能关中断或改 MPU，系统调用是唯一受控入口。它同时要求 SVC 入口、参数校验、用户栈与内核栈切换、指针合法性检查、上下文保存和额外的调试路径，成本落在每个提交点和每个异常入口上。

在业务代码由项目维护、模块边界清楚、没有不可信第三方代码的前提下，这些风险可以用更便宜的方式覆盖：MPU 给关键线程划分数据区与栈 guard，代码和常量只读，数据区不可执行，API 封装禁止业务直接触碰寄存器和内核对象，watchdog、预算与 fault handler 处理跑飞和死循环。残余风险是特权态业务仍可主动关中断或改 MPU，这由代码审查、保护寄存器访问收口和独立 watchdog 降低，本文不宣称消除。

因此默认路线不是“先做用户态再谈安全”，而是“先用静态边界换取可验证的误写保护”。只有产品要求业务无法绕过保护，或任意业务异常后其他域必须继续运行时，才另立用户态与独立恢复设计。

## 6. 故障处置与受控恢复

### 6.1 区分两类故障

| 情形 | 默认动作 | 允许局部恢复的条件 |
|---|---|---|
| 处理函数返回后的超时、准入违规 | 记录、拒绝或沿用逐 AO Breaker | 合作式静止点，框架数据未损坏 |
| 明确的业务故障上报 | 停域并由可信管理路径处理 | 业务资源可撤销，重建回调有明确契约 |
| MPU 异常、栈损坏、可信数据不变量破坏 | 平台故障入口执行产品安全动作/复位 | 仅当栈与框架状态完整、异常退出和资源撤销均可证明时另行开放；不是启用 MPU 就能重启 |
| 故障归属不明或重复恢复失败 | 系统级安全动作/复位 | 不自动重试 |

Breaker 是过载状态机，不是硬件安全输出，也不终止正在运行的 HSM。默认 Runtime 已按 AO 保存 Breaker，逻辑域停用状态另行管理；不得仅把 Breaker 设为 Safe 后就声称故障域已停止。

### 6.2 合作式停域协议

以下是拟新增的管理协议，不代表现有 Runtime 已支持。

1. 将域置为关闭准入，禁止该域目标的新任务/ISR 提交和直发；等待已进入提交管线的操作结束，并通知应用停止相关 timer、协程和外部生产者。
2. 在所有域内 AO 租约空闲后，由 Dispatcher 丢弃该域的排队和 deferred 事件；每个槽位按原路径完成 pending、容量预约和引用释放，批量回收必须 flush。不得让生产者任意摘除共享队列元素。
3. 证明该域所有持有者已退出；再调用显式、无分配的业务重建回调，重置 Context/HSM 和外设状态。不得强制清除仍被持有的租约，不得 memset AO 或重置共享池。
4. 完成健康探测后重新开放准入；设置有限重试次数和观察窗口，失败保持关闭并升级产品安全动作。

共享优先级队列中旧域事件可能被持续高优先级流量推迟。恢复实现必须选择关闭期间不重开、等待旧槽位全部排空的有界方案；若需要提前重开，则必须增加可验证的代际标记，防止旧事件作用于新实例。

`StagingSlot` 当前有尺寸不增长断言，见 `include/coact/staging.hpp:95`。不能未经容量/ABI 评估直接加 epoch 字段。先采用静止后排空方案；若无法给出排空上界，域保持关闭，不宣称重启成功。

跨 AO 扇出的事件可能仍被健康域持有，池注册也属于初始化生命周期。恢复只释放故障域持有的引用，不注销或重建仍被使用的池；禁止把所有池 `used()==0` 作为局部恢复条件。

故障记录使用固定容量可信存储，至少记录故障类别、目标/域、执行路径、时间、预算与耗时、恢复次数。硬件异常另记有效的 PC/SP/状态寄存器/故障地址；异常入口不分配、不阻塞、不遍历业务队列，不从损坏栈返回继续执行。

### 8.1 P1 实现与实测

P1 的交付物是编译期可选、默认零代码的准入策略，以及按 Config 显式启用的快照环。验证分五类，命令与原始输出见 `test/renode/README.md`。

| 层 | 命令 | 实测 |
|---|---|---|
| host 单元与并发 | `cmake --build build-v2 -j8`、`ctest --test-dir build-v2` | 57/57 通过；准入专项 41 组、711 个断言 |
| Renode 主夹具 | `test/renode/run.sh` | 231/231 通过（baseline 15 条，S1 至 S14） |
| Renode 变异 | `test/renode/mutate.sh` | 13/13 变异被捕获 |
| 看门狗 | `test/renode/wdg.sh` | 7/7；不返回的动作在 31899 us 被 IWDG 复位 |
| MPU | `test/renode/mpu.sh` | 13/13；能力 11/11，设计要求项 8/8 |

关键数据：

- `ArrivalGate` 在 Cortex-M4 上为 24 字节，仅含普通字段。`Cfg::kMaxAo=2` 时策略对象 88 字节（12 字节临界区钩子、4 字节对齐填充、3 个门），协调器从 32 字节增至 120 字节，ISR 版本同为 120 字节。
- 主夹具 ELF 的准入提交路径没有 `__atomic_compare_exchange_8` 调用点。框架代码中的 64 位原子调用只出现在显式启用的快照环（`fetch_add_8`、`load_8`、`store_8`），由 `runtime.c` 的关中断 64 位实现承载；其余 `load_8` 来自夹具断言读取 64 位计数器，不属于准入判定。
- 快照环默认 0 槽：`Monitor<NoSnapCfg>` 为 280 字节，启用 8 槽的 `Monitor<Cfg>` 为 544 字节。关闭策略节省的是提交路径代码与状态，诊断存储按配置单独计价，两者不能合并成“零成本”。环的序号与计数使用 64 位，避免 2^32 条记录后序号回绕成 0；这条诊断路径本来就需要 64 位原子。
- host 并发用例对 8 槽环写入 4 万条记录并由单读者循环读取，实测 `mixed=0`。`consistent` 与 `torn` 的比例随调度变化，`mixed=0` 才是 seqlock 的断言目标；`kTorn` 是允许的读失败，不是数据损坏。
- 回滚语义由持有计数覆盖：多个预约交错、其中部分失败时，窗口只由成功提交推进。变异 `rollback_restores_timestamp` 的首个失败断言是 `S2.gate.last_after_rollback`，S3 与 S10 的窗口断言随后也失败。
- Runtime 透传准入策略由真实 Runtime（POSIX PAL）端到端用例覆盖；该用例的两次提交在调用线程串行发起，验证的是转发与访问器，不是并发准入。

Renode 是功能模型，以上数据证明机制成立，不证明硅片时序、真实中断延迟或产品板 MPU 条目预算。

### 8.2 平台能力确认门禁

本节结论必须是具体开发板、芯片修订版本、RTOS/BSP 配置和工具链的实测或一手文档结论，不能以同一系列其他芯片、参考 RS300 移植或通用 CMSIS 行为替代。每项结论记录证据位置、验证命令或测试记录，以及不满足时的阻断决定。

| 能力项 | 必须确认的内容 | 未通过时的决定 |
|---|---|---|
| 保护单元与条目 | 实际 MPU/PMP 类型、可用区域数、最小/最大区域尺寸与对齐、重叠和背景映射语义；扣除 RTOS 已占用条目后，coact 还有多少可用条目 | 区域预算不足则缩小保护范围或停止 P3，不假定 8/16 条 |
| 特权访问权限 | coact 代码与 RTOS 线程实际执行态，以及该态下只读、禁止访问、不可执行属性的生效规则；确认代码可执行、常量只读、数据区不可执行的目标配置可表达 | 目标属性在特权态无效则调整方案，不把 API 封装计作硬件防护 |
| 异常入口与现场保存 | 目标异常向量、触发条件、异常栈、现场寄存器可获取性，以及与 RTOS 故障处理链的接管或共存方式；能否记录 PC/SP/故障地址后进入确定的安全动作 | 无法可靠进入或无法保存现场则停止 P4；共享栈损坏不得作为可恢复故障处理 |
| RTOS 协作 | 上下文切换是否保存和恢复保护状态，线程栈地址与大小能否静态获取，中断内配置切换的屏蔽要求，以及是否已启用 OS 级地址空间保护 | 与 RTOS 规划冲突时先确定唯一所有者；禁止 coact 与 RTOS 各自重写 MPU 配置 |
| 内存布局 | 链接脚本、map 和启动流程可给出代码、只读数据、关键数据、线程栈和未使用区边界；确认局部 static、字符串池化和对齐填充不会落入错误区域 | 布局无法闭合则先修链接规划，不进入 P3 |
| 故障处置 | 独立 watchdog 或平台超时通道可用，安全动作与复位路径有确定时限；该通道不依赖可能已损坏的业务线程 | 缺少独立处置通道则 P4 只能验证检测，不能宣称安全动作完备 |
| 验证环境 | 具备目标板或经确认的等效硬件环境，可执行受控越界、权限篡改和异常注入；Renode 等仿真器仅在模型覆盖上述硬件语义时用于补充 | 无等效环境则不接受 P3/P4 验收 |

门禁输出是一份平台能力结论和冻结的保护配置草案。任一阻断项未关闭，P3/P4 不得通过“部分支持”“以后补齐”或运行时静默降级的方式继续。

Renode 夹具可以作为“机制成立”的补充证据，但不能替代本门禁：主夹具证明 PRIMASK 临界区下的任务/ISR 准入计数、回滚与快照环；看门狗夹具证明 IWDG 在 31.9 ms 内终止不返回的动作；MPU 夹具证明该模型对栈 guard、只读区、不可执行区和非特权访问的强制行为（`CFSR=0x00000092`，`MMFAR=0x200008f4` 落在 guard 内）。它不证明硅片行为、真实时序、RTOS 上下文切换后的配置保持，也不证明产品板的 MPU 条目预算。
